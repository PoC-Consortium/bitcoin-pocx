## Параметри блоку генезису

### Обчислення базової цілі

**Формула**: `genesis_base_target = 2^42 / block_time_seconds`

**Обґрунтування**:
- Кожен nonce представляє 256 KiB (64 байти × 4096 scoops)
- 1 TiB = 2^22 nonces (припущення початкової потужності мережі)
- Очікувана мінімальна якість для n nonces ≈ 2^64 / n
- Для 1 TiB: E(quality) = 2^64 / 2^22 = 2^42
- Отже: base_target = 2^42 / block_time

**Обчислені значення**:
- Mainnet/Testnet/Signet (120с): `36650387592`
- Regtest (1с): Використовує режим калібрування низької ємності

### Повідомлення генезису

Each network has its own genesis message. See `src/kernel/chainparams.cpp` for details.

## Параметри консенсусу

### Параметри таймінгу

**MAX_FUTURE_BLOCK_TIME**: `15` секунд
- Специфічний для PoCX (Bitcoin використовує 2 години)
- Обґрунтування: Таймінг PoC вимагає валідації майже в реальному часі
- Блоки більш ніж на 15с у майбутньому відхиляються

**Попередження зміщення часу**: `10` секунд
- Операторів попереджають коли годинник вузла відхиляється >10с від мережевого часу
- Без примусового виконання, лише інформаційне

**Цільовий час блоку**:
- Mainnet/Testnet/Signet: `120` секунд
- Regtest: `1` секунда

**TIMESTAMP_WINDOW**: `15` секунд (дорівнює MAX_FUTURE_BLOCK_TIME)

**Реалізація**: `src/chain.h`, `src/validation.cpp`

### Параметри налаштування складності

**Розмір ковзного вікна**: `24` блоки (усі мережі)
- Експоненційне ковзне середнє недавніх часів блоків
- Налаштування кожного блоку
- Реагує на зміни ємності

**Реалізація**: `src/consensus/params.h`, логіка складності в створенні блоку

### Параметри системи призначень

**nForgingAssignmentDelay** (затримка активації):
- Mainnet: `30` блоків (~1 година)
- Testnet: `30` блоків (~1 година)
- Regtest: `4` блоки (~4 секунди)

**nForgingRevocationDelay** (затримка скасування):
- Mainnet: `720` блоків (~24 години)
- Testnet: `720` блоків (~24 години)
- Regtest: `8` блоків (~8 секунд)

**Обґрунтування**:
- Затримка активації запобігає швидкому перепризначенню під час гонок блоків
- Затримка скасування забезпечує стабільність та запобігає зловживанням

**Реалізація**: `src/consensus/params.h`

## Coinbase та винагороди за блоки

### Графік субсидії блоку

**Початкова субсидія**: `10 BTC` (усі мережі)

**Графік халвінгу**:
- Кожні `1050000` блоків (mainnet/testnet)
- Кожні `500` блоків (regtest)
- Продовжується максимум 64 халвінги

**Прогресія халвінгу**:
```
Халвінг 0: 10.00000000 BTC  (блоки 0 - 1049999)
Халвінг 1:  5.00000000 BTC  (блоки 1050000 - 2099999)
Халвінг 2:  2.50000000 BTC  (блоки 2100000 - 3149999)
Халвінг 3:  1.25000000 BTC  (блоки 3150000 - 4199999)
...
```

**Загальна пропозиція**: ~21 мільйон BTC (так само як Bitcoin)

### Правила виходу Coinbase

**Призначення платежу**:
- **Без призначення**: Coinbase платить адресі плоту (proof.account_id)
- **З призначенням**: Coinbase платить адресі кування (ефективний підписант)

**Формат виходу**: Тільки P2WPKH
- Coinbase повинен платити на bech32 SegWit v0 адресу
- Генерується з публічного ключа ефективного підписанта

**Вирішення призначення**:
```cpp
effective_signer = GetEffectiveSigner(plot_address, height, view);
coinbase_script = P2WPKH(effective_signer);
```

**Реалізація**: `src/pocx/mining/block_builder.cpp:BuildBlock()`

## Динамічне масштабування

### Межі масштабування

**Призначення**: Збільшення складності генерації плотів у міру дозрівання мережі для запобігання інфляції ємності

**Структура**:
```cpp
struct PoCXCompressionBounds {
    uint32_t nPoCXMinCompression;     // Мінімальний прийнятний рівень
    uint32_t nPoCXTargetCompression;  // Рекомендований рівень
};
```

**Співвідношення**: `target = min + 1` (завжди на один рівень вище мінімуму)

### Графік збільшення масштабування

Рівні масштабування збільшуються за **експоненційним графіком** на основі інтервалів халвінгу:

| Період часу | Висота блоку | Халвінги | Min | Target |
|-------------|--------------|----------|-----|--------|
| Роки 0-4 | 0 до 1049999 | 0 | X1 | X2 |
| Роки 4-12 | 1050000 до 3149999 | 1-2 | X2 | X3 |
| Роки 12-28 | 3150000 до 7349999 | 3-6 | X3 | X4 |
| Роки 28-60 | 7350000 до 15749999 | 7-14 | X4 | X5 |
| Роки 60-124 | 15750000 до 32549999 | 15-30 | X5 | X6 |
| Роки 124+ | 32550000+ | 31+ | X6 | X7 |

**Ключові висоти** (роки → халвінги → блоки):
- Рік 4: Халвінг 1 на блоці 1050000
- Рік 12: Халвінг 3 на блоці 3150000
- Рік 28: Халвінг 7 на блоці 7350000
- Рік 60: Халвінг 15 на блоці 15750000
- Рік 124: Халвінг 31 на блоці 32550000

### Складність рівня масштабування

**Масштабування PoW**:
- Рівень масштабування X0: Базовий рівень POC2 (теоретичний)
- Рівень масштабування X1: Базовий рівень XOR-transpose
- Рівень масштабування Xn: 2^(n-1) × вбудована робота X1
- Кожен рівень подвоює роботу генерації плоту

**Економічне вирівнювання**:
- Винагороди за блоки зменшуються вдвічі → складність генерації плотів зростає
- Підтримує запас безпеки: вартість створення плоту > вартість пошуку
- Запобігає інфляції ємності від покращень обладнання

### Валідація плотів

**Правила валідації**:
- Подані докази повинні мати рівень масштабування ≥ мінімуму
- Докази з масштабуванням > цільового приймаються, але неефективні
- Докази нижче мінімуму: відхиляються (недостатньо PoW)

**Отримання меж**:
```cpp
auto bounds = GetPoCXCompressionBounds(height, halving_interval);
```

**Реалізація**: `src/pocx/consensus/params.h:GetPoCXCompressionBounds()`, `src/pocx/consensus/params.cpp`

## Конфігурація P2P протоколу

### Версія протоколу

**База**: Протокол Bitcoin Core v30.2
- **Версія протоколу**: Успадкована від Bitcoin Core
- **Service Bits**: Стандартні сервіси Bitcoin
- **Типи повідомлень**: Стандартні P2P повідомлення Bitcoin

**Розширення PoCX**:
- Заголовки блоків включають специфічні для PoCX поля
- Повідомлення блоків включають дані доказу PoCX
- Правила валідації забезпечують консенсус PoCX

**Сумісність**: Вузли PoCX несумісні з вузлами Bitcoin PoW (різний консенсус)

**Реалізація**: `src/protocol.h`, `src/net_processing.cpp`

## Структура каталогу даних

### Каталог за замовчуванням

**Розташування**: `.bitcoin/` (так само як Bitcoin Core)
- Linux: `~/.bitcoin/`
- macOS: `~/Library/Application Support/Bitcoin/`
- Windows: `%APPDATA%\Bitcoin\`

### Вміст каталогу

```
.bitcoin/
├── blocks/              # Дані блоків
│   ├── blk*.dat        # Файли блоків
│   ├── rev*.dat        # Дані скасування
│   └── index/          # Індекс блоків (LevelDB)
├── chainstate/         # Набір UTXO + призначення кування (LevelDB)
├── wallets/            # Файли гаманця
│   └── wallet.dat      # Гаманець за замовчуванням
├── bitcoin.conf        # Файл конфігурації
├── debug.log           # Лог налагодження
├── peers.dat           # Адреси пірів
├── mempool.dat         # Персистентність mempool
└── banlist.dat         # Заблоковані піри
```

### Ключові відмінності від Bitcoin

**База даних Chainstate**:
- Стандартно: Набір UTXO
- **Доповнення PoCX**: Стан призначень кування
- Атомарні оновлення: UTXO + призначення оновлюються разом
- Безпечні для реорганізацій дані скасування для призначень

**Файли блоків**:
- Стандартний формат блоку Bitcoin
- **Доповнення PoCX**: Розширені полями доказу PoCX (account_id, seed, nonce, signature, pubkey)

### Приклад файлу конфігурації

**bitcoin.conf**:
```ini
# Вибір мережі
#testnet=1
#regtest=1

# Сервер майнінгу PoCX (потрібен для зовнішніх майнерів)

# Налаштування RPC
server=1
rpcuser=yourusername
rpcpassword=yourpassword
rpcallowip=127.0.0.1
rpcport=8332

# Налаштування з'єднання
listen=1
port=8338
maxconnections=125

# Цільовий час блоку (інформаційний, консенсус забезпечує)
# 120 секунд для mainnet/testnet
```
