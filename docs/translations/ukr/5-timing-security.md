# Розділ 5: Синхронізація часу та безпека

## Огляд

Консенсус PoCX вимагає точної синхронізації часу в усій мережі. Цей розділ документує механізми безпеки, пов'язані з часом, допуск дрейфу годинника та поведінку захисного кування.

**Ключові механізми**:
- 15-секундний допуск на майбутнє для міток часу блоків
- 10-секундна система попередження про дрейф годинника
- Захисне кування (захист від маніпуляцій з годинником)
- Інтеграція алгоритму Time Bending

## Вимоги до синхронізації часу

### Константи та параметри

**Конфігурація Bitcoin-PoCX:**
```cpp
// src/chain.h
static constexpr int64_t MAX_FUTURE_BLOCK_TIME = 15;  // 15 секунд

// src/node/timeoffsets.h
static constexpr std::chrono::seconds WARN_THRESHOLD{10};  // 10 секунд
```

### Перевірки валідації

**Валідація мітки часу блоку** (`src/validation.cpp:ContextualCheckBlockHeader()`):
```cpp
// 1. Перевірка монотонності: мітка часу >= мітка часу попереднього блоку
if (block.nTime < pindexPrev->nTime) {
    return state.Invalid("time-too-old");
}

// 2. Перевірка на майбутнє: мітка часу <= зараз + 15 секунд
if (block.Time() > NodeClock::now() + std::chrono::seconds{MAX_FUTURE_BLOCK_TIME}) {
    return state.Invalid("time-too-new");
}

// 3. Перевірка дедлайну: минулий час >= дедлайн
uint32_t elapsed_time = block.nTime - pindexPrev->nTime;
if (poc_time > elapsed_time) {
    return state.Invalid("bad-pocx-timing");
}
```

### Таблиця впливу дрейфу годинника

| Зміщення годинника | Синхронізація? | Майнінг? | Статус валідації | Конкурентний ефект |
|-------------------|----------------|----------|------------------|-------------------|
| -30с повільний | ❌ НІ - Перевірка майбутнього провалюється | Н/Д | **МЕРТВИЙ ВУЗОЛ** | Не може брати участь |
| -14с повільний | ✅ Так | ✅ Так | Пізнє кування, проходить валідацію | Програє гонки |
| 0с ідеальний | ✅ Так | ✅ Так | Оптимально | Оптимально |
| +14с швидкий | ✅ Так | ✅ Так | Раннє кування, проходить валідацію | Виграє гонки ⚠️ |
| +16с швидкий | ✅ Так | ❌ Перевірка майбутнього провалюється | Не може розповсюджувати блоки | Може синхронізуватися, не може майнити |

**Ключове розуміння**: 15-секундне вікно симетричне для участі (±14.9с), але швидкі годинники надають нечесну конкурентну перевагу в межах допуску.

### Інтеграція Time Bending

Алгоритм Time Bending (детально в [Розділі 3](3-consensus-and-mining.md#time-bending-calculation)) трансформує сирі дедлайни за допомогою кубічного кореня:

```
time_bended_deadline = scale × (deadline_seconds)^(1/3)
```

**Взаємодія з дрейфом годинника**:
- Кращі рішення куються раніше (кубічний корінь підсилює різницю якості)
- Дрейф годинника впливає на час кування відносно мережі
- Захисне кування забезпечує конкуренцію на основі якості попри варіацію таймінгу

## Виявлення дрейфу годинника та попередження

### Система попереджень

Bitcoin-PoCX моніторить зміщення часу між локальним вузлом та мережевими пірами.

**Повідомлення попередження** (коли дрейф перевищує 10 секунд):
> "Дата та час вашого комп'ютера, схоже, відстають від мережі більш ніж на 10 секунд, це може призвести до провалу консенсусу PoCX. Будь ласка, перевірте системний годинник."

**Реалізація**: `src/node/timeoffsets.cpp`

### Обґрунтування проектування

**Чому 10 секунд?**
- Забезпечує 5-секундний запас безпеки до 15-секундного ліміту допуску
- Суворіше ніж за замовчуванням у Bitcoin Core (10 хвилин)
- Відповідає вимогам таймінгу PoC

**Превентивний підхід**:
- Раннє попередження до критичного провалу
- Дозволяє операторам проактивно вирішувати проблеми
- Зменшує фрагментацію мережі через проблеми, пов'язані з часом

## Механізм захисного кування

### Що це таке

Захисне кування — це стандартна поведінка майнера в Bitcoin-PoCX, що усуває переваги на основі таймінгу в виробництві блоків. Коли ваш майнер отримує конкуруючий блок на тій самій висоті, він автоматично перевіряє чи маєте ви краще рішення. Якщо так, він негайно кує ваш блок, забезпечуючи конкуренцію на основі якості, а не маніпуляцій з годинником.

### Проблема

Консенсус PoCX дозволяє блоки з мітками часу до 15 секунд у майбутньому. Цей допуск необхідний для глобальної мережевої синхронізації. Однак він створює можливість для маніпуляцій з годинником:

**Без захисного кування:**
- Майнер A: Правильний час, якість 800 (краща), чекає належного дедлайну
- Майнер B: Швидкий годинник (+14с), якість 1000 (гірша), кує на 14 секунд раніше
- Результат: Майнер B виграє гонку попри гірший proof-of-capacity

**Проблема:** Маніпуляція годинником надає перевагу навіть з гіршою якістю, підриваючи принцип proof-of-capacity.

### Рішення: Дворівневий захист

#### Рівень 1: Попередження про дрейф годинника (превентивний)

Bitcoin-PoCX моніторить зміщення часу між вашим вузлом та мережевими пірами. Якщо ваш годинник відхиляється більш ніж на 10 секунд від мережевого консенсусу, ви отримуєте попередження про необхідність виправлення проблем з годинником до того, як вони спричинять проблеми.

#### Рівень 2: Захисне кування (реактивний)

Коли інший майнер публікує блок на тій самій висоті, яку ви майните:

1. **Виявлення**: Ваш вузол ідентифікує конкуренцію на тій самій висоті
2. **Валідація**: Витягує та валідує якість конкуруючого блоку
3. **Порівняння**: Перевіряє чи ваша якість краща
4. **Відповідь**: Якщо краща, негайно кує ваш блок

**Результат:** Мережа отримує обидва блоки та вибирає той з кращою якістю через стандартне вирішення форків.

### Як це працює

#### Сценарій: Конкуренція на тій самій висоті

```
Час 150с: Майнер B (годинник +10с) кує з якістю 1000
           → Мітка часу блоку показує 160с (10с у майбутньому)

Час 150с: Ваш вузол отримує блок Майнера B
           → Виявляє: та сама висота, якість 1000
           → У вас: якість 800 (краща!)
           → Дія: Негайно кувати з правильною міткою часу (150с)

Час 152с: Мережа валідує обидва блоки
           → Обидва валідні (в межах 15с допуску)
           → Якість 800 виграє (менше = краще)
           → Ваш блок стає верхівкою ланцюга
```

#### Сценарій: Справжня реорганізація

```
Ваша висота майнінгу 100, конкурент публікує блок 99
→ Не конкуренція на тій самій висоті
→ Захисне кування НЕ спрацьовує
→ Нормальна обробка реорганізації продовжується
```

### Переваги

**Нульовий стимул для маніпуляцій з годинником**
- Швидкі годинники допомагають лише якщо у вас і так найкраща якість
- Маніпуляція годинником стає економічно безглуздою

**Забезпечення конкуренції на основі якості**
- Примушує майнерів конкурувати на основі реальної proof-of-capacity роботи
- Зберігає цілісність консенсусу PoCX

**Мережева безпека**
- Стійкість до стратегій ігор на основі таймінгу
- Не потребує змін консенсусу - чиста поведінка майнера

**Повністю автоматичний**
- Не потребує конфігурації
- Спрацьовує лише коли необхідно
- Стандартна поведінка в усіх вузлах Bitcoin-PoCX

### Компроміси

**Мінімальне збільшення частоти осиротілих блоків**
- Навмисне - атакуючі блоки осиротіють
- Відбувається лише під час фактичних спроб маніпуляції годинником
- Природний результат вирішення форків на основі якості

**Коротка мережева конкуренція**
- Мережа короткочасно бачить два конкуруючі блоки
- Вирішується за секунди через стандартну валідацію
- Така ж поведінка як одночасний майнінг в Bitcoin

### Технічні деталі

**Вплив на продуктивність:** Незначний
- Спрацьовує лише при конкуренції на тій самій висоті
- Використовує дані в пам'яті (без дискового I/O)
- Валідація завершується за мілісекунди

**Використання ресурсів:** Мінімальне
- ~20 рядків основної логіки
- Повторно використовує існуючу інфраструктуру валідації
- Одне захоплення блокування

**Сумісність:** Повна
- Без змін правил консенсусу
- Працює з усіма функціями Bitcoin Core
- Опціональний моніторинг через debug логи

**Статус**: Активний у всіх релізах Bitcoin-PoCX
**Вперше введено**: 10 жовтня 2025

## Аналіз загроз безпеки

### Атака швидкого годинника (пом'якшена захисним куванням)

**Вектор атаки**:
Майнер з годинником **на +14с вперед** може:
1. Отримувати блоки нормально (вони виглядають старими для нього)
2. Негайно кувати блоки коли дедлайн мине
3. Транслювати блоки, що виглядають на 14с "рано" для мережі
4. **Блоки приймаються** (в межах 15с допуску)
5. **Виграє гонки** проти чесних майнерів

**Вплив без захисного кування**:
Перевага обмежена 14.9 секундами (недостатньо щоб пропустити значну PoC роботу), але надає постійну перевагу в гонках блоків.

**Пом'якшення (захисне кування)**:
- Чесні майнери виявляють конкуренцію на тій самій висоті
- Порівнюють значення якості
- Негайно куються якщо якість краща
- **Результат**: Швидкий годинник допомагає лише якщо у вас вже найкраща якість
- **Стимул**: Нульовий - маніпуляція годинником стає економічно безглуздою

### Провал повільного годинника (критичний)

**Режим провалу**:
Вузол **>15с позаду** є катастрофічним:
- Не може валідувати вхідні блоки (перевірка майбутнього провалюється)
- Стає ізольованим від мережі
- Не може майнити або синхронізуватися

**Пом'якшення**:
- Суворе попередження при 10с дрейфу дає 5-секундний буфер до критичного провалу
- Оператори можуть проактивно виправити проблеми з годинником
- Чіткі повідомлення про помилки допомагають в усуненні несправностей

## Найкращі практики для операторів вузлів

### Налаштування синхронізації часу

**Рекомендована конфігурація**:
1. **Увімкніть NTP**: Використовуйте Network Time Protocol для автоматичної синхронізації
   ```bash
   # Linux (systemd-timesyncd)
   sudo timedatectl set-ntp true

   # Перевірка статусу
   timedatectl status
   ```

2. **Перевірте точність годинника**: Регулярно перевіряйте зміщення часу
   ```bash
   # Перевірка статусу синхронізації NTP
   ntpq -p

   # Або з chrony
   chronyc tracking
   ```

3. **Моніторте попередження**: Слідкуйте за попередженнями Bitcoin-PoCX про дрейф годинника в логах

### Для майнерів

**Дії не потрібні**:
- Функція завжди активна
- Працює автоматично
- Просто тримайте системний годинник точним

**Найкращі практики**:
- Використовуйте синхронізацію часу NTP
- Моніторте попередження про дрейф годинника
- Негайно реагуйте на попередження якщо вони з'являються

**Очікувана поведінка**:
- Соло-майнінг: Захисне кування рідко спрацьовує (немає конкуренції)
- Мережевий майнінг: Захищає від спроб маніпуляції годинником
- Прозора робота: Більшість майнерів ніколи цього не помічає

### Усунення несправностей

**Попередження: "10 секунд розсинхронізації"**
- Дія: Перевірте та виправте синхронізацію системного годинника
- Вплив: 5-секундний буфер до критичного провалу
- Інструменти: NTP, chrony, systemd-timesyncd

**Помилка: "time-too-new" на вхідних блоках**
- Причина: Ваш годинник відстає більш ніж на 15 секунд
- Вплив: Не може валідувати блоки, вузол ізольований
- Виправлення: Негайно синхронізуйте системний годинник

**Помилка: Неможливо розповсюдити сковані блоки**
- Причина: Ваш годинник випереджає більш ніж на 15 секунд
- Вплив: Блоки відхиляються мережею
- Виправлення: Негайно синхронізуйте системний годинник

## Проектні рішення та обґрунтування

### Чому 15-секундний допуск?

**Обґрунтування**:
- Змінний таймінг дедлайнів Bitcoin-PoCX менш критичний до часу ніж консенсус з фіксованим таймінгом
- 15с забезпечує адекватний захист водночас запобігаючи фрагментації мережі

**Компроміси**:
- Жорсткіший допуск = більше фрагментації мережі від незначного дрейфу
- Вільніший допуск = більше можливостей для атак на таймінг
- 15с балансує безпеку та надійність

### Чому 10-секундне попередження?

**Міркування**:
- Забезпечує 5-секундний запас безпеки
- Більш доречне для PoC ніж 10-хвилинне значення за замовчуванням Bitcoin
- Дозволяє проактивні виправлення до критичного провалу

### Чому захисне кування?

**Вирішена проблема**:
- 15-секундний допуск дозволяє перевагу швидкого годинника
- Консенсус на основі якості міг би бути підірваний маніпуляціями з таймінгом

**Переваги рішення**:
- Безкоштовний захист (без змін консенсусу)
- Автоматична робота
- Усуває стимул для атак
- Зберігає принципи proof-of-capacity

### Чому немає внутрішньомережевої синхронізації часу?

**Міркування безпеки**:
- Сучасний Bitcoin Core видалив налаштування часу на основі пірів
- Вразливий до Sybil-атак на сприйняття мережевого часу
- PoCX навмисно уникає покладання на внутрішні мережеві джерела часу
- Системний годинник надійніший ніж консенсус пірів
- Оператори повинні синхронізуватися за допомогою NTP або еквівалентного зовнішнього джерела часу
- Вузли моніторять власний дрейф та видають попередження якщо локальний годинник відхиляється від недавніх міток часу блоків
