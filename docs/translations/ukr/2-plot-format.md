# Розділ 2: Специфікація формату плотів PoCX

Цей документ описує формат плотів PoCX — покращену версію формату POC2 з підвищеною безпекою, оптимізацією SIMD та масштабованим proof-of-work.

## Огляд формату

Файли плотів PoCX містять попередньо обчислені значення хешів Shabal256, організовані для ефективних операцій майнінгу. Дотримуючись традиції PoC з часів POC1, **усі метадані вбудовані в ім'я файлу** — заголовка файлу немає.

### Розширення файлу
- **Стандартне**: `.pocx` (завершені плоти)
- **В процесі**: `.tmp` (під час побудови плоту, перейменовується на `.pocx` після завершення)

## Історичний контекст та еволюція вразливостей

### Формат POC1 (застарілий)
**Дві основні вразливості (компроміси часу та пам'яті):**

1. **Вада розподілу PoW**
   - Нерівномірний розподіл proof-of-work між scoops
   - Низькі номери scoops можна було обчислити на льоту
   - **Вплив**: Зменшені вимоги до сховища для атакуючих

2. **Атака XOR-стиснення** (50% компроміс часу та пам'яті)
   - Експлуатувала математичні властивості для досягнення 50% зменшення сховища
   - **Вплив**: Атакуючі могли майнити з половиною необхідного сховища

**Оптимізація структури**: Базова послідовна структура scoops для ефективності HDD

### Формат POC2 (Burstcoin)
- ✅ **Виправлено ваду розподілу PoW**
- ❌ **Вразливість XOR-transpose залишилася невиправленою**
- **Структура**: Збережено послідовну оптимізацію scoops

### Формат PoCX (поточний)
- ✅ **Виправлено розподіл PoW** (успадковано від POC2)
- ✅ **Усунено вразливість XOR-transpose** (унікально для PoCX)
- ✅ **Покращена структура SIMD/GPU** оптимізована для паралельної обробки та об'єднання пам'яті
- ✅ **Масштабований proof-of-work** запобігає компромісам часу та пам'яті зі зростанням обчислювальної потужності (PoW виконується лише при створенні або оновленні файлів плотів)

## XOR-Transpose кодування

### Проблема: 50% компроміс часу та пам'яті

У форматах POC1/POC2 атакуючі могли експлуатувати математичний зв'язок між scoops, щоб зберігати лише половину даних і обчислювати решту на льоту під час майнінгу. Ця "атака XOR-стиснення" підривала гарантію сховища.

### Рішення: XOR-Transpose загартування

PoCX отримує свій формат майнінгу (X1) шляхом застосування XOR-transpose кодування до пар базових warps (X0):

**Для побудови scoop S nonce N у warp X1:**
1. Візьміть scoop S nonce N з першого warp X0 (пряма позиція)
2. Візьміть scoop N nonce S з другого warp X0 (транспонована позиція)
3. XOR двох 64-байтових значень для отримання scoop X1

Крок транспонування міняє місцями індекси scoop та nonce. У матричних термінах — де рядки представляють scoops, а стовпці представляють nonces — це поєднує елемент у позиції (S, N) у першому warp з елементом у (N, S) у другому.

### Чому це усуває атаку

XOR-transpose блокує кожен scoop з цілим рядком та цілим стовпцем базових даних X0. Відновлення одного scoop X1 вимагає доступу до даних, що охоплюють усі 4096 індексів scoops. Будь-яка спроба обчислити відсутні дані вимагала б регенерації 4096 повних nonces, а не одного nonce — усуваючи асиметричну структуру витрат, яку експлуатувала атака XOR.

Як результат, зберігання повного warp X1 стає єдиною обчислювально життєздатною стратегією для майнерів.

## Структура метаданих імені файлу

Усі метадані плоту закодовані в імені файлу за цим точним форматом:

```
{ACCOUNT_PAYLOAD}_{SEED}_{WARPS}_{SCALING}.pocx
```

### Компоненти імені файлу

1. **ACCOUNT_PAYLOAD** (40 шістнадцяткових символів)
   - Сирий 20-байтовий payload облікового запису як шістнадцятковий у верхньому регістрі
   - Незалежний від мережі (без ідентифікатора мережі або контрольної суми)
   - Приклад: `DEADBEEFCAFEBABE1337C0DEBADC0FFEE15DEAD0`

2. **SEED** (64 шістнадцяткових символи)
   - 32-байтове значення seed як шістнадцяткове в нижньому регістрі
   - **Нове в PoCX**: Випадковий 32-байтовий seed в імені файлу замінює послідовну нумерацію nonce — запобігає перекриттю плотів
   - Приклад: `C0FFEEBEEFCAFEBABEDEADBEEF1337C0DE42424242FEEDFACECAFED00DABAD1D`

3. **WARPS** (десяткове число)
   - **Нова одиниця розміру в PoCX**: Замінює розмірність на основі nonce з POC1/POC2
   - **Дизайн стійкий до XOR-transpose**: Кожен warp = рівно 4096 nonces (розмір розділу, необхідний для стійкої до XOR-transpose трансформації)
   - **Розмір**: 1 warp = 1073741824 байти = 1 GiB (зручна одиниця)
   - Приклад: `1024` (плот 1 TiB = 1024 warps)

4. **SCALING** (десяткове з префіксом X)
   - Рівень масштабування як `X{рівень}`
   - Вищі значення = більше proof-of-work потрібно
   - Приклад: `X4` (2^4 = 16× складність POC2)

### Приклади імен файлів
```
DEADBEEFCAFEBABE1337C0DEBADC0FFEE15DEAD_C0FFEEBEEFCAFEBABEDEADBEEF1337C0DE42424242FEEDFACECAFED00DABAD1D_1024_X4.pocx
FEEDFACEDEADC0DE123456789ABCDEF012345678_B00B1E5FEEDC0DEBABEFACE5DEA1DEADC0DE1337C0FFEEBABEFACE5BAD1DEA50_2048_X1.pocx
```


## Структура файлу та організація даних

### Ієрархічна організація
```
Файл плоту (БЕЗ ЗАГОЛОВКА)
├── Scoop 0
│   ├── Warp 0 (Усі nonces для цього scoop/warp)
│   ├── Warp 1
│   └── ...
├── Scoop 1
│   ├── Warp 0
│   ├── Warp 1
│   └── ...
└── Scoop 4095
    ├── Warp 0
    └── ...
```

### Константи та розміри

| Константа       | Розмір                  | Опис                                            |
| --------------- | ----------------------- | ----------------------------------------------- |
| **HASH\_SIZE**  | 32 B                   | Вивід одного хешу Shabal256                     |
| **SCOOP\_SIZE** | 64 B (2 × HASH\_SIZE)  | Пара хешів, що читається в раунді майнінгу      |
| **NUM\_SCOOPS** | 4096 (2¹²)             | Scoops на nonce; один обирається за раунд       |
| **NONCE\_SIZE** | 262144 B (256 KiB)     | Усі scoops nonce (найменша одиниця PoC1/PoC2)   |
| **WARP\_SIZE**  | 1073741824 B (1 GiB)   | Найменша одиниця в PoCX                         |

### Структура файлу плоту, оптимізована для SIMD

PoCX реалізує патерн доступу до nonce з урахуванням SIMD, що дозволяє векторизовану обробку
кількох nonces одночасно. Вона базується на концепціях з [дослідження оптимізації POC2×16](https://www.reddit.com/r/burstcoin/comments/a1qyoq/cip_announcement_poc2x16_a_new_optimized_plot/) для максимізації пропускної здатності пам'яті та ефективності SIMD.

---

#### Традиційна послідовна структура

Послідовне зберігання nonces:

```
[Nonce 0: Дані Scoop] [Nonce 1: Дані Scoop] [Nonce 2: Дані Scoop] ...
```

Неефективність SIMD: Кожна SIMD-лінія потребує того самого слова з різних nonces:

```
Word 0 з Nonce 0 -> зміщення 0
Word 0 з Nonce 1 -> зміщення 512
Word 0 з Nonce 2 -> зміщення 1024
...
```

Доступ scatter-gather зменшує пропускну здатність.

---

#### Структура PoCX, оптимізована для SIMD

PoCX зберігає **позиції слів з 16 nonces** суміжно:

```
Рядок кешу (64 байти):

Word0_N0 Word0_N1 Word0_N2 ... Word0_N15
Word1_N0 Word1_N1 Word1_N2 ... Word1_N15
...
```

**ASCII-діаграма**

```
Традиційна структура:

Nonce0: [W0][W1][W2][W3]...
Nonce1: [W0][W1][W2][W3]...
Nonce2: [W0][W1][W2][W3]...

Структура PoCX:

Word0: [N0][N1][N2][N3]...[N15]
Word1: [N0][N1][N2][N3]...[N15]
Word2: [N0][N1][N2][N3]...[N15]
```

---

#### Переваги доступу до пам'яті

- Один рядок кешу забезпечує всі SIMD-лінії.
- Усуває операції scatter-gather.
- Зменшує промахи кешу.
- Повністю послідовний доступ до пам'яті для векторизованих обчислень.
- GPU також виграють від 16-nonce вирівнювання, максимізуючи ефективність кешу.

---

#### Масштабування SIMD

| SIMD       | Ширина вектора* | Nonces | Циклів обробки на рядок кешу |
|------------|-----------------|--------|------------------------------|
| SSE2/AVX   | 128-біт         | 4      | 4 цикли                      |
| AVX2       | 256-біт         | 8      | 2 цикли                      |
| AVX512     | 512-біт         | 16     | 1 цикл                       |

\* Для цілочисельних операцій

---



## Масштабування Proof-of-Work

### Рівні масштабування
- **X0**: Базові nonces без XOR-transpose кодування (теоретичний, не використовується для майнінгу)
- **X1**: XOR-transpose базовий рівень — перший загартований формат (1× робота)
- **X2**: 2× робота X1 (XOR через 2 warps)
- **X3**: 4× робота X1 (XOR через 4 warps)
- **…**
- **Xn**: 2^(n-1) × вбудована робота X1

### Переваги
- **Регульована складність PoW**: Збільшує обчислювальні вимоги для підтримки темпу зі швидшим обладнанням
- **Довговічність формату**: Дозволяє гнучке масштабування складності майнінгу з часом

### Оновлення плотів / Зворотна сумісність

Коли мережа збільшує шкалу PoW (Proof of Work) на 1, існуючі плоти потребують оновлення для підтримки того самого ефективного розміру плоту. По суті, тепер вам потрібно вдвічі більше PoW у ваших файлах плотів для досягнення того самого внеску у ваш обліковий запис.

Добра новина в тому, що PoW, який ви вже виконали при створенні файлів плотів, не втрачається — вам просто потрібно додати додатковий PoW до існуючих файлів. Немає потреби перебудовувати плоти.

Альтернативно, ви можете продовжувати використовувати поточні плоти без оновлення, але зверніть увагу, що тепер вони будуть вносити лише 50% свого попереднього ефективного розміру у ваш обліковий запис. Ваше програмне забезпечення майнінгу може масштабувати файл плоту на льоту.

## Порівняння із застарілими форматами

| Особливість | POC1 | POC2 | PoCX |
|-------------|------|------|------|
| Розподіл PoW | ❌ Вадний | ✅ Виправлено | ✅ Виправлено |
| Стійкість до XOR-Transpose | ❌ Вразливий | ❌ Вразливий | ✅ Виправлено |
| Оптимізація SIMD | ❌ Немає | ❌ Немає | ✅ Розширена |
| Оптимізація GPU | ❌ Немає | ❌ Немає | ✅ Оптимізовано |
| Масштабований Proof-of-Work | ❌ Немає | ❌ Немає | ✅ Так |
| Підтримка Seed | ❌ Немає | ❌ Немає | ✅ Так |

Формат PoCX представляє сучасний стан технології у форматах плотів Proof of Capacity, усуваючи всі відомі вразливості та водночас забезпечуючи значні покращення продуктивності для сучасного обладнання.
