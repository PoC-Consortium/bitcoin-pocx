## Параметри на генезис блок

### Изчисляване на базова цел

**Формула**: `genesis_base_target = 2^42 / block_time_seconds`

**Обосновка**:
- Всеки nonce представлява 256 KiB (64 байта × 4096 scoops)
- 1 TiB = 2^22 nonces (предположение за начален мрежов капацитет)
- Очаквано минимално качество за n nonces ≈ 2^64 / n
- За 1 TiB: E(quality) = 2^64 / 2^22 = 2^42
- Следователно: base_target = 2^42 / block_time

**Изчислени стойности**:
- Mainnet/Testnet/Signet (120s): `36650387592`
- Regtest (1s): Използва режим на калибриране с нисък капацитет

### Съобщение на генезис

Each network has its own genesis message. See `src/kernel/chainparams.cpp` for details.

## Консенсусни параметри

### Параметри за време

**MAX_FUTURE_BLOCK_TIME**: `15` секунди
- Специфичен за PoCX (Bitcoin използва 2 часа)
- Обосновка: PoC времето изисква почти реално време за валидация
- Блокове, повече от 15s в бъдеще, се отхвърлят

**Предупреждение за отклонение на време**: `10` секунди
- Операторите се предупреждават, когато часовникът на възела се отклони >10s от мрежовото време
- Без прилагане, само информационно

**Целеви времена на блок**:
- Mainnet/Testnet/Signet: `120` секунди
- Regtest: `1` секунда

**TIMESTAMP_WINDOW**: `15` секунди (равно на MAX_FUTURE_BLOCK_TIME)

**Имплементация**: `src/chain.h`, `src/validation.cpp`

### Параметри за корекция на трудност

**Размер на плаващ прозорец**: `24` блока (всички мрежи)
- Експоненциална плаваща средна на последните времена на блокове
- Корекция при всеки блок
- Реагира на промени в капацитета

**Имплементация**: `src/consensus/params.h`, логика за трудност в създаването на блок

### Параметри на системата за делегиране

**nForgingAssignmentDelay** (забавяне на активиране):
- Mainnet: `30` блока (~1 час)
- Testnet: `30` блока (~1 час)
- Regtest: `4` блока (~4 секунди)

**nForgingRevocationDelay** (забавяне на отмяна):
- Mainnet: `720` блока (~24 часа)
- Testnet: `720` блока (~24 часа)
- Regtest: `8` блока (~8 секунди)

**Обосновка**:
- Забавянето на активиране предотвратява бързо пределегиране по време на надпревари за блокове
- Забавянето на отмяна предоставя стабилност и предотвратява злоупотреба

**Имплементация**: `src/consensus/params.h`

## Coinbase и награди за блок

### График на субсидии за блок

**Начална субсидия**: `10 BTC` (всички мрежи)

**График на halving**:
- На всеки `1050000` блока (mainnet/testnet)
- На всеки `500` блока (regtest)
- Продължава за максимум 64 halvings

**Прогресия на halving**:
```
Halving 0: 10.00000000 BTC  (блокове 0 - 1049999)
Halving 1:  5.00000000 BTC  (блокове 1050000 - 2099999)
Halving 2:  2.50000000 BTC  (блокове 2100000 - 3149999)
Halving 3:  1.25000000 BTC  (блокове 3150000 - 4199999)
...
```

**Общо предлагане**: ~21 милиона BTC (същото като Bitcoin)

### Правила за Coinbase изход

**Дестинация на плащане**:
- **Без делегиране**: Coinbase плаща на адреса на plot (proof.account_id)
- **С делегиране**: Coinbase плаща на адреса за подписване (ефективен подписващ)

**Формат на изход**: Само P2WPKH
- Coinbase трябва да плаща към bech32 SegWit v0 адрес
- Генерира се от публичния ключ на ефективния подписващ

**Резолюция на делегиране**:
```cpp
effective_signer = GetEffectiveSigner(plot_address, height, view);
coinbase_script = P2WPKH(effective_signer);
```

**Имплементация**: `src/pocx/mining/block_builder.cpp:BuildBlock()`

## Динамично мащабиране

### Граници на мащабиране

**Цел**: Увеличаване на трудността за генериране на plot файлове с узряването на мрежата за предотвратяване на инфлация на капацитет

**Структура**:
```cpp
struct PoCXCompressionBounds {
    uint32_t nPoCXMinCompression;     // Минимално приемано ниво
    uint32_t nPoCXTargetCompression;  // Препоръчително ниво
};
```

**Връзка**: `target = min + 1` (винаги едно ниво над минимума)

### График за увеличаване на мащабирането

Нивата на мащабиране се увеличават по **експоненциален график** на база интервали на halving:

| Времеви период | Височина на блок | Halvings | Min | Target |
|----------------|------------------|----------|-----|--------|
| Години 0-4 | 0 до 1049999 | 0 | X1 | X2 |
| Години 4-12 | 1050000 до 3149999 | 1-2 | X2 | X3 |
| Години 12-28 | 3150000 до 7349999 | 3-6 | X3 | X4 |
| Години 28-60 | 7350000 до 15749999 | 7-14 | X4 | X5 |
| Години 60-124 | 15750000 до 32549999 | 15-30 | X5 | X6 |
| Години 124+ | 32550000+ | 31+ | X6 | X7 |

**Ключови височини** (години → halvings → блокове):
- Година 4: Halving 1 на блок 1050000
- Година 12: Halving 3 на блок 3150000
- Година 28: Halving 7 на блок 7350000
- Година 60: Halving 15 на блок 15750000
- Година 124: Halving 31 на блок 32550000

### Трудност на ниво на мащабиране

**PoW мащабиране**:
- Ниво на мащабиране X0: POC2 базова линия (теоретично)
- Ниво на мащабиране X1: XOR-transpose базова линия
- Ниво на мащабиране Xn: 2^(n-1) × X1 работа вградена
- Всяко ниво удвоява работата за генериране на plot

**Икономическо съответствие**:
- Наградите за блок се преполовяват → трудността за генериране на plot се увеличава
- Поддържа се предпазен марж: разходи за създаване на plot > разходи за търсене
- Предотвратява инфлация на капацитет от подобрения в хардуера

### Валидация на Plot

**Правила за валидация**:
- Подадените доказателства трябва да имат ниво на мащабиране ≥ минимум
- Доказателства с мащабиране > target се приемат, но са неефективни
- Доказателства под минимума: отхвърлят се (недостатъчен PoW)

**Извличане на граници**:
```cpp
auto bounds = GetPoCXCompressionBounds(height, halving_interval);
```

**Имплементация**: `src/pocx/consensus/params.h:GetPoCXCompressionBounds()`, `src/pocx/consensus/params.cpp`

## Конфигурация на P2P протокол

### Версия на протокол

**База**: Bitcoin Core v30.2 протокол
- **Версия на протокол**: Наследена от Bitcoin Core
- **Service bits**: Стандартни Bitcoin услуги
- **Типове съобщения**: Стандартни Bitcoin P2P съобщения

**PoCX разширения**:
- Заглавията на блокове включват PoCX-специфични полета
- Съобщенията за блок включват PoCX данни за доказателство
- Правилата за валидация прилагат PoCX консенсус

**Съвместимост**: PoCX възлите са несъвместими с Bitcoin PoW възли (различен консенсус)

**Имплементация**: `src/protocol.h`, `src/net_processing.cpp`

## Структура на директория с данни

### Директория по подразбиране

**Местоположение**: `.bitcoin/` (същото като Bitcoin Core)
- Linux: `~/.bitcoin/`
- macOS: `~/Library/Application Support/Bitcoin/`
- Windows: `%APPDATA%\Bitcoin\`

### Съдържание на директория

```
.bitcoin/
├── blocks/              # Данни за блокове
│   ├── blk*.dat        # Файлове с блокове
│   ├── rev*.dat        # Undo данни
│   └── index/          # Индекс на блокове (LevelDB)
├── chainstate/         # UTXO set + делегирания за подписване (LevelDB)
├── wallets/            # Файлове на портфейл
│   └── wallet.dat      # Портфейл по подразбиране
├── bitcoin.conf        # Конфигурационен файл
├── debug.log           # Debug лог
├── peers.dat           # Адреси на пиъри
├── mempool.dat         # Персистенция на mempool
└── banlist.dat         # Забранени пиъри
```

### Ключови разлики от Bitcoin

**База данни Chainstate**:
- Стандартно: UTXO set
- **PoCX добавка**: Състояние на делегиране за подписване
- Атомарни актуализации: UTXO + делегирания се актуализират заедно
- Undo данни, безопасни при реорганизации, за делегирания

**Файлове с блокове**:
- Стандартен Bitcoin формат на блок
- **PoCX добавка**: Разширени с PoCX полета за доказателство (account_id, seed, nonce, signature, pubkey)

### Примерен конфигурационен файл

**bitcoin.conf**:
```ini
# Избор на мрежа
#testnet=1
#regtest=1

# PoCX mining сървър (необходим за външни миньори)

# RPC настройки
server=1
rpcuser=yourusername
rpcpassword=yourpassword
rpcallowip=127.0.0.1
rpcport=8332

# Настройки на връзка
listen=1
port=8338
maxconnections=125

# Целево време на блок (информационно, консенсусът прилага)
# 120 секунди за mainnet/testnet
```
