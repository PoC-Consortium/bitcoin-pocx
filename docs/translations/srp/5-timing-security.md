# Поглавље 5: Синхронизација времена и безбедност

## Преглед

PoCX консензус захтева прецизну синхронизацију времена преко мреже. Ово поглавље документује механизме безбедности везане за време, толеранцију одступања сата и понашање дефанзивног ковања.

**Кључни механизми**:
- 15-секундна толеранција будућности за временске ознаке блокова
- Систем упозорења за одступање сата од 10 секунди
- Дефанзивно ковање (против манипулације сатом)
- Интеграција алгоритма савијања времена

## Захтеви синхронизације времена

### Константе и параметри

**Bitcoin-PoCX конфигурација:**
```cpp
// src/chain.h
static constexpr int64_t MAX_FUTURE_BLOCK_TIME = 15;  // 15 секунди

// src/node/timeoffsets.h
static constexpr std::chrono::seconds WARN_THRESHOLD{10};  // 10 секунди
```

### Провере валидације

**Валидација временске ознаке блока** (`src/validation.cpp:ContextualCheckBlockHeader()`):
```cpp
// 1. Монотона провера: временска ознака >= временска ознака претходног блока
if (block.nTime < pindexPrev->nTime) {
    return state.Invalid("time-too-old");
}

// 2. Провера будућности: временска ознака <= сада + 15 секунди
if (block.Time() > NodeClock::now() + std::chrono::seconds{MAX_FUTURE_BLOCK_TIME}) {
    return state.Invalid("time-too-new");
}

// 3. Провера рока: протекло време >= рок
uint32_t elapsed_time = block.nTime - pindexPrev->nTime;
if (poc_time > elapsed_time) {
    return state.Invalid("bad-pocx-timing");
}
```

### Табела утицаја одступања сата

| Одступање сата | Може синхронизовати? | Може рударити? | Статус валидације | Конкурентни ефекат |
|----------------|---------------------|----------------|-------------------|-------------------|
| -30s споро | ❌ НЕ - Провера будућности не успева | N/A | **МРТАВ ЧВОР** 💀 | Не може учествовати |
| -14s споро | ✅ Да | ✅ Да | Касно ковање, пролази валидацију | Губи трке |
| 0s савршено | ✅ Да | ✅ Да | Оптимално | Оптимално |
| +14s брзо | ✅ Да | ✅ Да | Рано ковање, пролази валидацију | Добија трке ⚠️ |
| +16s брзо | ✅ Да | ❌ Провера будућности не успева | Не може ширити блокове | Може синхронизовати, не може рударити |

**Кључни увид**: Прозор од 15 секунди је симетричан за учешће (±14.9s), али брзи сатови пружају неправедну конкурентну предност унутар толеранције.

### Интеграција савијања времена

Алгоритам савијања времена (детаљно у [Поглавље 3](3-consensus-and-mining.md#израчунавање-савијања-времена)) трансформише сирове рокове користећи кубни корен:

```
time_bended_deadline = scale × (deadline_seconds)^(1/3)
```

**Интеракција са одступањем сата**:
- Боља решења се кују раније (кубни корен појачава разлике у квалитету)
- Одступање сата утиче на време ковања у односу на мрежу
- Дефанзивно ковање обезбеђује конкуренцију засновану на квалитету упркос варијанси времена

---

## Детекција одступања сата и упозорења

### Систем упозорења

Bitcoin-PoCX надгледа временски офсет између локалног чвора и мрежних пирова.

**Порука упозорења** (када одступање прелази 10 секунди):
> "Изгледа да су датум и време вашег рачунара више од 10 секунди ван синхронизације са мрежом, ово може довести до неуспеха PoCX консензуса. Молимо проверите системски сат."

**Имплементација**: `src/node/timeoffsets.cpp`

### Образложење дизајна

**Зашто 10 секунди?**
- Обезбеђује 5-секундни сигурносни бафер пре ограничења толеранције од 15 секунди
- Строжије од подразумеваног Bitcoin Core (10 минута)
- Прикладно за захтеве PoC времена

**Превентивни приступ**:
- Рано упозорење пре критичног неуспеха
- Омогућава оператерима да проактивно поправе проблеме
- Смањује фрагментацију мреже од неуспеха везаних за време

## Механизам дефанзивног ковања

### Шта је то

Дефанзивно ковање је стандардно понашање рудара у Bitcoin-PoCX које елиминише предности засноване на времену у производњи блокова. Када ваш рудар прими конкурентски блок на истој висини, аутоматски проверава да ли имате боље решење. Ако имате, одмах кује ваш блок, обезбеђујући конкуренцију засновану на квалитету уместо конкуренције засноване на манипулацији сатом.

### Проблем

PoCX консензус дозвољава блокове са временским ознакама до 15 секунди у будућности. Ова толеранција је неопходна за глобалну синхронизацију мреже. Међутим, ствара могућност за манипулацију сатом:

**Без дефанзивног ковања:**
- Рудар A: Тачно време, квалитет 800 (бољи), чека правилан рок
- Рудар B: Брз сат (+14s), квалитет 1000 (лошији), кује 14 секунди раније
- Резултат: Рудар B побеђује у трци упркос инфериорном proof-of-capacity раду

**Проблем:** Манипулација сатом пружа предност чак и са лошијим квалитетом, подривајући принцип proof-of-capacity.

### Решење: Двослојна одбрана

#### Слој 1: Упозорење о одступању сата (превентивно)

Bitcoin-PoCX надгледа временски офсет између вашег чвора и мрежних пирова. Ако ваш сат одступи више од 10 секунди од консензуса мреже, примате упозорење које вас упозорава да поправите проблеме са сатом пре него што изазову проблеме.

#### Слој 2: Дефанзивно ковање (реактивно)

Када други рудар објави блок на истој висини коју ви рударите:

1. **Детекција**: Ваш чвор идентификује конкуренцију на истој висини
2. **Валидација**: Извлачи и валидира квалитет конкурентског блока
3. **Поређење**: Проверава да ли је ваш квалитет бољи
4. **Одговор**: Ако је бољи, одмах кује ваш блок

**Резултат:** Мрежа прима оба блока и бира онај са бољим квалитетом кроз стандардно разрешавање вилице.

### Како функционише

#### Сценарио: Конкуренција на истој висини

```
Време 150s: Рудар B (сат +10s) кује са квалитетом 1000
           → Временска ознака блока показује 160s (10s у будућности)

Време 150s: Ваш чвор прима блок рудара B
           → Детектује: иста висина, квалитет 1000
           → Ви имате: квалитет 800 (бољи!)
           → Акција: Кују одмах са тачном временском ознаком (150s)

Време 152s: Мрежа валидира оба блока
           → Оба важећа (унутар 15s толеранције)
           → Квалитет 800 побеђује (нижи = бољи)
           → Ваш блок постаје врх ланца
```

#### Сценарио: Прави реорг

```
Ваша висина рударења 100, конкурент објављује блок 99
→ Није конкуренција на истој висини
→ Дефанзивно ковање СЕ НЕ активира
→ Наставља нормално руковање реоргом
```

### Предности

**Нема подстицаја за манипулацију сатом**
- Брзи сатови помажу само ако већ имате најбољи квалитет
- Манипулација сатом постаје економски бесмислена

**Спроведена конкуренција заснована на квалитету**
- Приморава рударе да се такмиче на стварном proof-of-capacity раду
- Чува интегритет PoCX консензуса

**Безбедност мреже**
- Отпорна на стратегије игре засноване на времену
- Не захтева промене консензуса - чисто понашање рудара

**Потпуно аутоматски**
- Не захтева конфигурацију
- Активира се само када је потребно
- Стандардно понашање у свим Bitcoin-PoCX чворовима

### Компромиси

**Минимално повећање стопе сирочади**
- Намерно - блокови напада постају сирочад
- Дешава се само током стварних покушаја манипулације сатом
- Природни резултат разрешавања вилице заснованог на квалитету

**Кратка мрежна конкуренција**
- Мрежа накратко види два конкурентска блока
- Разрешава се у секундама кроз стандардну валидацију
- Исто понашање као истовремено рударење у Bitcoin-у

### Технички детаљи

**Утицај на перформансе:** Занемарљив
- Активира се само при конкуренцији на истој висини
- Користи податке у меморији (без I/O диска)
- Валидација се завршава у милисекундама

**Употреба ресурса:** Минимална
- ~20 линија основне логике
- Поново користи постојећу инфраструктуру валидације
- Једно преузимање закључавања

**Компатибилност:** Потпуна
- Без промена правила консензуса
- Ради са свим Bitcoin Core функцијама
- Опционо надгледање преко debug логова

**Статус**: Активно у свим Bitcoin-PoCX издањима
**Прво представљено**: 2025-10-10

## Анализа безбедносних претњи

### Напад брзим сатом (ублажен дефанзивним ковањем)

**Вектор напада**:
Рудар са сатом **+14s унапред** може:
1. Примати блокове нормално (изгледају му стари)
2. Ковати блокове одмах када рок прође
3. Емитовати блокове који изгледају 14s "рано" мрежи
4. **Блокови се прихватају** (унутар 15s толеранције)
5. **Побеђује у тркама** против поштених рудара

**Утицај без дефанзивног ковања**:
Предност је ограничена на 14.9 секунди (није довољно да се прескочи значајан PoC рад), али пружа конзистентну предност у тркама блокова.

**Ублажење (дефанзивно ковање)**:
- Поштени рудари детектују конкуренцију на истој висини
- Упоређују вредности квалитета
- Одмах кују ако је квалитет бољи
- **Резултат**: Брз сат помаже само ако већ имате најбољи квалитет
- **Подстицај**: Нула - манипулација сатом постаје економски бесмислена

### Неуспех спорог сата (критичан)

**Режим неуспеха**:
Чвор **>15s иза** је катастрофалан:
- Не може валидирати долазеће блокове (провера будућности не успева)
- Постаје изолован од мреже
- Не може рударити или синхронизовати

**Ублажење**:
- Снажно упозорење при 10s одступања даје 5-секундни бафер пре критичног неуспеха
- Оператери могу проактивно поправити проблеме са сатом
- Јасне поруке о грешкама воде решавање проблема

## Најбоље праксе за оператере чворова

### Подешавање синхронизације времена

**Препоручена конфигурација**:
1. **Омогућите NTP**: Користите Network Time Protocol за аутоматску синхронизацију
   ```bash
   # Linux (systemd-timesyncd)
   sudo timedatectl set-ntp true

   # Проверите статус
   timedatectl status
   ```

2. **Верификујте тачност сата**: Редовно проверавајте временски офсет
   ```bash
   # Проверите статус NTP синхронизације
   ntpq -p

   # Или са chrony
   chronyc tracking
   ```

3. **Надгледајте упозорења**: Пратите Bitcoin-PoCX упозорења о одступању сата у логовима

### За рударе

**Није потребна акција**:
- Функција је увек активна
- Ради аутоматски
- Само одржавајте системски сат тачним

**Најбоље праксе**:
- Користите NTP синхронизацију времена
- Надгледајте упозорења о одступању сата
- Одмах адресирајте упозорења ако се појаве

**Очекивано понашање**:
- Соло рударење: Дефанзивно ковање се ретко активира (нема конкуренције)
- Мрежно рударење: Штити од покушаја манипулације сатом
- Транспарентна операција: Већина рудара то никада не примети

### Решавање проблема

**Упозорење: "10 секунди ван синхронизације"**
- Акција: Проверите и поправите синхронизацију системског сата
- Утицај: 5-секундни бафер пре критичног неуспеха
- Алати: NTP, chrony, systemd-timesyncd

**Грешка: "time-too-new" на долазећим блоковима**
- Узрок: Ваш сат је >15 секунди споро
- Утицај: Не може валидирати блокове, чвор изолован
- Решење: Синхронизујте системски сат одмах

**Грешка: Не може ширити исковане блокове**
- Узрок: Ваш сат је >15 секунди брзо
- Утицај: Блокове одбија мрежа
- Решење: Синхронизујте системски сат одмах

## Дизајнерске одлуке и образложење

### Зашто 15-секундна толеранција?

**Образложење**:
- Bitcoin-PoCX варијабилно време рока је мање критично за време од консензуса са фиксним временом
- 15s пружа адекватну заштиту док спречава фрагментацију мреже

**Компромиси**:
- Строжа толеранција = више фрагментације мреже од мањег одступања
- Лабавија толеранција = више могућности за нападе засноване на времену
- 15s балансира безбедност и робусност

### Зашто 10-секундно упозорење?

**Образложење**:
- Обезбеђује 5-секундни сигурносни бафер
- Прикладније за PoC од подразумеваних 10 минута Bitcoin-а
- Омогућава проактивне поправке пре критичног неуспеха

### Зашто дефанзивно ковање?

**Адресирани проблем**:
- 15-секундна толеранција омогућава предност брзог сата
- Консензус заснован на квалитету могао би бити подриван манипулацијом времена

**Предности решења**:
- Одбрана без трошкова (без промена консензуса)
- Аутоматска операција
- Елиминише подстицај за напад
- Чува принципе proof-of-capacity

### Зашто нема интра-мрежне синхронизације времена?

**Безбедносно образложење**:
- Модеран Bitcoin Core је уклонио подешавање времена засновано на пировима
- Рањиво на Sybil нападе на перципирано мрежно време
- PoCX намерно избегава ослањање на интерне изворе времена мреже
- Системски сат је поузданији од консензуса пирова
- Оператери треба да синхронизују користећи NTP или еквивалентни спољни извор времена
- Чворови надгледају своје одступање и емитују упозорења ако локални сат дивергира од недавних временских ознака блокова
